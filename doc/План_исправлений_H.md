## H-1. Удаление оригиналов: явная передача настройки

**Проблема.** `Main.ps1:795/809` передаёт `-DeleteOriginal` только при «Yes». При «No» `AnalyzeFiles.ps1:49` использует `Settings.psd1` (по умолчанию `1`).

**Решение (согласовано: явная передача).**

- `AnalyzeFiles.ps1`: заменить switch `-DeleteOriginal` на обязательный параметр `-DeleteOriginals` с `[ValidateSet(0,1)]`. Убрать ветку `PSBoundParameters.ContainsKey`.
- `Main.ps1`: **всегда** передавать значение явно:
  - пользовательский режим: из выбора («Yes» → 1, «No» → 0);
  - Quick start: значение из `Settings.psd1` (`General.DeleteOriginals`), прочитанное в `Main`, а не в анализаторе.
- Одноразовое понижение до `0` из-за отсутствия корзины (M-9) применяется в анализе (см. H-1/M-9 ниже) и **не** пишет в `Settings.psd1`.

**Совместимость.** Одиночный файл (`-SingleFile`): `Main` тоже передаёт значение явно из настроек.

**Тесты (Windows).**
- Custom → «No», `Settings.DeleteOriginals = 1`: исходники на месте, в `PlanOptions.DeleteOriginals = false`.
- Custom → «Yes», `Settings.DeleteOriginals = 0`: исходники в корзине.
- Quick, `Settings = 1`: в корзине. Quick, `Settings = 0`: на месте.

**Открытый вопрос.** Нужно ли в пользовательском режиме показывать итоговое решение о судьбе оригиналов в сводке плана («Оригиналы: сохранить / в корзину»)? Предлагаю показывать.

## H-2. Коллизии выходных имён: резервирование на этапе построения плана

**Проблема.** Имя `.avif` вычисляется при запуске задачи (`CompressPhotos.ps1:336`, `Get-UniqueOutputPath`), не резервируется. Одинаковые базовые имена (`IMG.jpg` + `IMG.png`) параллельно пишут в один `.ACtmp`.

**Решение (согласовано: на этапе плана, суффикс `_порядковый номер`).**

Алгоритм в `BuildEncodingPlan.ps1` (новая функция `Reserve-OutputPaths`):

1. Кандидаты сортируются детерминированно (по полному пути без учёта регистра).
2. Целевой путь: `dir\base.<ext>`, где `<ext>` = `avif` или `webp` (анимированный GIF).
3. Ключ резервирования: полный путь в нижнем регистре. Набор `HashSet` в памяти.
4. Путь свободен, если он: не занят другой задачей плана, не существует на диске и не совпадает с **исходным файлом** (например, `photo.avif` как исходник не бывает, но защищаемся явно).
5. Если путь занят, пробуем `base_2.<ext>`, `base_3.<ext>` и т.д. Первый кандидат получает имя без суффикса.
6. `OutputPath` записывается в задачу плана. `Get-UniqueOutputPath` в `CompressPhotos` **не вызывается**. Вместо него задача использует готовый путь. Если файл появился на диске после построения плана, задача пропускается с предупреждением (`OutputCollision`), а не перезаписывает файл.
7. Защита от перезаписи: `Rename-TempToFinal` больше не удаляет существующий файл. Если финальный путь уже существует, это ошибка задачи.

**Совместимость.**
- Резюме-план (`EncodingPlan_Resume.clixml`), созданный старой версией без `OutputPath`: при загрузке, если поля нет, `CompressPhotos` вычисляет путь прежним способом с той же защитой (проверка существования и skip при коллизии).
- Правило `OutputExists` в анализе для групп с одинаковым базовым именем (`sameBaseCount > 1`) пересматривается: существующий `base.avif` считается занятым, и применяется суффикс.

**Тесты (Windows).**
- `IMG.jpg` + `IMG.png` + `IMG.bmp` (параллельность ≥ 2): получаются `IMG.avif`, `IMG_2.avif`, `IMG_3.avif`; ни один исходник не потерян, нет `.ACtmp`.
- `photo.jpg`, `photo.png`, `photo_2.jpg`: `photo_2.avif` не занимается дважды (резервирование учитывает и исходные имена).
- `IMG.avif` уже на диске: новый результат получает `IMG_2.avif`.
- Резюме старого формата продолжает работать.

**Открытые вопросы (нужно решение владельца).**
1. Кто получает «базовое» имя без суффикса? Предлагаю первый по сортировке полного пути.
2. Первый дубликат получает `_2` или `_1`? Предлагаю `_2`: `_1` уже используется текущим кодом для коллизии с существующим файлом, и смешивание путает.

## H-3. Классификация «повреждён» vs «не удалось прочитать»

**Проблема.** `ImageProbe.ps1:489/509`: любой сбой ffmpeg даёт `$canDecode = $false` → файл в `_corrupt/`. Так же обрабатываются заблокированные файлы и файлы OneDrive «только в сети».

**Решение.** Три результата вместо двух, в `Test-CanDecode`:

| Результат | Условие | Действие |
|---|---|---|
| `Decodable` | ffmpeg отработал, ошибок декодирования нет | как сейчас: `UnsupportedMetadata`, предупреждение |
| `Corrupt` | файл **открыт успешно**, ffmpeg завершился и его stderr содержит явный признак формата (`Invalid data found when processing input`, `Decode error`, `0 bytes left`) | `_corrupt/` и `corrupt.log` |
| `Unreadable` | `OpenRead` не удался (блокировка), ffmpeg не запустился, таймаут, атрибуты файла `Offline`/`RecallOnDataAccess` (облачный файл), любое другое сообщение | **не перемещать**, пропуск, строка в `warnings.log` с причиной `Unreadable` |

Дополнительно:
- Перед стадией 4 проверяется наличие `ffmpeg` (уже есть в `Test-RequiredTools`, добавить проверку запуска).
- Классификация по stderr консервативна: при неизвестном сообщении файл не перемещается.
- Раздел в отчёте анализа (сводка) получает счётчик `Unreadable`.

**Тесты (Windows).**
- Файл, открытый в эксклюзивном режиме другой программой: `Unreadable`, не перемещён.
- OneDrive «только онлайн»: `Unreadable`.
- Обрезанный JPG (или намеренно испорченный файл с сигнатурой): `Corrupt` (проверить, какой текст выдаёт ffmpeg, и зафиксировать паттерн в тесте).
- Файл без ffmpeg в PATH: анализ останавливается до стадии 4.

## H-4. Альфа в fallback для PNG

**Текущая команда fallback для PNG с альфой** (`AvifDirect`, `HasAlpha = true`; при дефолтных настройках, пакетный режим). Фактические строки записываются в лог при срабатывании fallback (`Fallback1:` / `Fallback2:`).

Шаг 1 (ffmpeg, `Build-FallbackArgs`, `ImageEncoding.ps1:94`):
```
ffmpeg -hide_banner -y -v error -i "<src>.png" -map 0:v:0 -frames:v 1 -pix_fmt yuv444p "<TEMP>\<guid>.png"
```

Шаг 2 (avifenc, аргументы из `AlphaPng`, `{input}`/`{output}` заменены):
```
avifenc "<TEMP>\<guid>.png" -s 5 -q 55 --qalpha 80 -r f --autotiling -a color:enable-chroma-deltaq=1 -a color:aq-mode=3 -a color:tune=iq -a color:sharpness=2 -j 4 "<out>.avif.ACtmp"
```
(`-j 4` только в пакетном режиме; `-s 5` = `Opaque.S + AlphaPng.SpeedDelta`.)

**Проблема.** `-pix_fmt yuv444p` переводит RGBA в YUV без альфы. Прозрачные пиксели становятся непрозрачными, и fallback успешно завершается.

**Предлагаемое решение.**
- Для альфа-случая использовать `-pix_fmt yuva444p`, как вы указали, **с оговоркой, которую нужно проверить**:
  - PNG-энкодер ffmpeg не принимает `yuva444p`. ffmpeg добавит автоматическое преобразование в `rgba`. Это лишний цикл RGBA → YUVA → RGBA с потерей точности.
  - Альтернатива: `-pix_fmt rgba` (нативный формат PNG с альфой) или вообще без `-pix_fmt`, чтобы сохранить исходный формат (палитра с `tRNS` тоже корректна).
  - Предлагаю **`rgba`**, если ваш тест на атрибутах не покажет иного. Решение за вами после проверки.
- Fallback для непрозрачного `AvifDirect` использовать `Settings.FFmpeg.StaticPixFmt` вместо жёсткого `yuv444p` (сейчас настройка игнорируется в fallback).
- Ошибка fallback остаётся явной: если альфа в промежуточном файле потеряна (проверка `ffprobe` на `pix_fmt`), задача завершается ошибкой `AlphaLost`, а не проходит тихо.

**Тесты (Windows).**
- PNG RGBA с полупрозрачными краями: primary и fallback дают AVIF с альфа-планом. Проверка: наличие альфа-плана в результате (инструмент уточнить на этапе тестов) и сравнение прозрачных пикселей.
- Палитровый PNG с `tRNS`: то же.
- Fallback на JPG без изменений по качеству (`StaticPixFmt`).

**Что нужно от вас.** Проверьте атрибуты под новый энкодер (по команде выше) и выберите вариант `-pix_fmt` для альфы: `yuva444p` / `rgba` / без параметра.

## H-5. Временные файлы сеанса и возобновление по Q

**Проблема.** `Main.ps1:546/559/832/845` проверяет только наличие `compress_analysis.clixml` и `compress_plan.clixml` в `%TEMP%`. Устаревший файл от прерванного сеанса запускает обработку старого списка.

**Решение.**

1. `Main.ps1` при каждом входе в обработку папки создаёт `SessionId` (GUID) и **удаляет** `compress_analysis.clixml` и `compress_plan.clixml` до запуска анализа.
2. `AnalyzeFiles.ps1` принимает `-SessionId` и записывает его в `compress_analysis.clixml`. Файл пишется **всегда**, включая выходы с нулевым числом кандидатов (`Candidates = @()`), чтобы отсутствие файла не означало «пусто».
3. `BuildEncodingPlan.ps1` принимает `-SessionId`, проверяет совпадение и отказывается работать при несовпадении (код выхода 1, сообщение). Записывает `SessionId` в план.
4. `CompressPhotos.ps1` проверяет `SessionId` плана. Ожидаемый `SessionId` передаётся из `Main` через параметр.
5. **Резюме по Q (важно):**
   - Файл `EncodingPlan_Resume.clixml` в **папке-источнике** не является временным. Он не удаляется по H-5 и не проверяется по `SessionId`.
   - Путь «Resume» в `Main.ps1` копирует резюме в `compress_plan.clixml`. Перед копированием `Main` **присваивает новый `SessionId`** (поле `PlanFile` уже переписывается тем же способом). Иначе проверка в `CompressPhotos` сломает продолжение.
   - Q-stop (`CompressPhotos.ps1:553`) продолжает писать резюме без изменений. Новое поле `SessionId` в резюме не нужно: оно создаётся заново при возобновлении.
   - Логика «Resume / Start over» (`Main.ps1:625–652`) не меняется; при возобновлении `Main` читает резюме на строке 652.
6. `Remove-TempFiles` и очистка `*.ACtmp` в папке-источнике остаются как есть.

**Тесты (Windows).**
- Подложить старый `compress_analysis.clixml` (от другой папки), запустить на пустой папке: стаб удалён, сообщение «нет файлов», обработки чужих файлов нет.
- Q-stop → перезапуск → «Resume»: продолжение с оставшимися задачами, все `OutputPath` сохранены (связка с H-2).
- Q-stop → «Start over»: резюме удалено, новый анализ.
- Обычный прогон: `SessionId` совпадает на всех стадиях.

## Связанные решения (предложения, без реализации до согласования)

Эти пункты вы зафиксировали в замечаниях; они связаны с H-1 и H-4, поэтому описаны здесь. Подробный план для остальных пунктов будет после согласования группы H.

### M-9. Корзина на диске источника

- В анализе проверяется корзина диска-источника. Кандидаты для проверки: наличие `<диск>:\$RECYCLE.BIN` или вызов `SHQueryRecycleBin` (shell32), который возвращает ошибку, если корзины нет.
- **Замечание:** наличие `$RECYCLE.BIN` не гарантирует, что корзина работает (пользователь может отключить «не перемещать в корзину» для диска). Предлагаю `SHQueryRecycleBin` как более точную проверку. Нужна проверка на Windows (сетевой диск, флешка, локальный NTFS, отключённая корзина).
- При понижении `DeleteOriginals` до `0` выводится **явное предупреждение** в сводке плана (не тихо). Это вариант, который вы описали, с выводом причины.

### M-10. Изменения `Settings.psd1` при запуске

- `Get-ParallelismSettings` при `AnalysisThreads > ядер` переписывает файл. Вы предлагаете обрабатывать так же, как ошибки валидации, но без прерывания.
- Предлагаемая схема: изменение записывается в список `ConfigWarnings`, выводится в `Main` как предупреждение («AnalysisThreads изменён: 32 → 8 (ядер: 8)») и пишется в лог. Процесс не останавливается. Файл при этом можно не трогать вообще (значение используется только в памяти), и тогда изменение не нужно сохранять.

### M-3. Fallback как фоновая задача с лимитом

- Лимит: `TimeoutSec = 0` (в т.ч. `TimeoutSecSingleFile = 0`) → **900 с**. Значения 1…900 применяются как есть. Значения больше 900 применяются без ограничения (как вы указали).
- Лимит для fallback — **общий на оба шага** (ffmpeg + avifenc), а не на каждый шаг. Иначе худший случай — 2× лимит.
- Реализация: задача получает стадию (`Primary` / `FallbackFFmpeg` / `FallbackAvifenc`). `Complete-Job` продвигает стадию и запускает следующий процесс вместо немедленной финализации. Так fallback не блокирует очередь.
- Общий механизм лимита нужен и для M-2 (см. ниже).

### M-2. Аварийное завершение и дочерние процессы

**Ответ на вопрос: нет, утечки памяти в самом PowerShell не будет, но проблема реальна.** При аварии (trap, kill, закрытие окна, Ctrl+C) родительский процесс PowerShell умирает, а `cmd`/`ffmpeg`/`avifenc` продолжают работать:

- процессы не убиваются и висят до конца работы (при зависании навсегда, особенно при `TimeoutSec = 0`);
- они потребляют память и CPU (`avifenc` до 2.5 ГБ по оценке в `Config.ps1`);
- продолжают писать `.ACtmp` в папку пользователя, и новый запуск может удалить `.ACtmp`, в который ещё пишут;
- Ctrl+C из консоли не доходит до процессов, созданных с `CreateNoWindow`, поэтому trap не вызывается и очистки нет.

**Предлагаемое решение: Windows Job Object.** Через `Add-Type` (P/Invoke: `CreateJobObject`, `SetInformationJobObject` с `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` и флагом `KILL_ON_JOB_CLOSE`, `AssignProcessToJobObject`) создаётся задание. Все запускаемые процессы (и их потомки, включая `cmd`) назначаются в задание. Когда родительский процесс завершается любым способом, ОС убивает всех потомков. Это решает аварии, kill и Ctrl+C без зависимости от trap. Дополнительно: очистка `.ACtmp` при старте по `SessionId` (H-5).

Проверить на Windows: поведение вложенных заданий (Windows 8+), совместимость с `cmd` и `CreateNoWindow`.

### M-1 и M-8. Единый установщик компонентов

**Что уже согласовано:** один скрипт с флагом компонента, хранение версии, даты релиза и общей даты последней проверки; проверка через страницу релиза вместо `api.github.com`; переименование папок установки в `tools\ACffmpeg`, `tools\ACavifenc`, `tools\ACgif2webp` (по аналогии с `.ACtmp`), чтобы однозначно искать старые записи PATH.

**Что, по моей оценке, не учтено (нужно решить):**

1. **Получение «последней версии» без API.** Варианты: `https://github.com/<repo>/releases/latest` возвращает `302` с тегом в `Location` (без API); `…/releases.atom` содержит теги и даты обновления. Для gyan.dev и Google Storage разбор страницы остаётся, и формат нужно проверить. Дата релиза может отсутствовать: тогда сравнение только по версии, а дата для отображения.
2. **Определение установленной версии.** `ffmpeg -version`, `avifenc --version`, `gif2webp -version`: формат вывода нужно проверить для каждого бинарника. Версию ffmpeg из сборки gyan.dev нужно парсить аккуратно.
3. **Где хранится состояние.** `installers/state.psd1` в git (M-11). Нужна отдельная игнорируемая запись состояния. Поле `LastUpdateCheck` общее, `Installed` и `ReleaseDate` на компонент. Текущий `Set-Psd1Value` (регулярное выражение) для вложенных структур не подходит: нужна полная перезапись файла.
4. **Политика проверки обновлений.** Не блокировать запуск: короткий таймаут (3–5 с), отказ сети не приводит к ошибке, интервал проверки (например, 24 ч), вариант «пропустить эту версию».
5. **Атомарное обновление.** Загрузка во временную папку → проверка (хеш, если источник его публикует; иначе размер и успешная распаковка) → распаковка в staging → переименование старой папки → перемещение новой → удаление старой только после успешного запуска `<tool> -version`. Откат при ошибке.
6. **Миграция.** Существующие установки `tools\ffmpeg` и т.п. нужно переименовать (или переустановить) и **удалить их записи из PATH** до переименования. Иначе `Get-Command` будет находить старые пути.
7. **Записи PATH.** Если PATH остаётся пользовательским, поиск по префиксу `tools\AC*` однозначен. Альтернатива: вообще не менять пользовательский PATH, а добавлять папки в `$env:Path` процесса в `Main.ps1`. Это устраняет побочные эффекты, но не даёт использовать инструменты вне программы. **Нужно решение.**
8. **Права.** Установка в папку проекта не требует прав администратора. Установка pwsh через MSI требует UAC. Вынести её из единого скрипта или оставить отдельно?
9. **Контрольные суммы.** Проверить, публикуют ли источники хеши (gyan.dev, libavif, libwebp). Если нет, проверка только по размеру и распаковке, и это нужно явно указать пользователю.
10. **Фиксация версий.** Обновляться до «latest» или фиксировать проверенную версию в конфиге? Предлагаю фиксацию по умолчанию с возможностью обновления.

### JP2 — бинарный парсер (дополнительно к плану)

- Сейчас JP2 идёт через ffprobe (`AnalysisGroup = 'Ffprobe'`). Новый парсер добавляется в группу `Binary` (в `ImageProbe.ps1`, встроенный в `ForEach-Object -Parallel`, как и GIF/WebP, т.к. функции недоступны в параллельном блоке).
- Разбор: сигнатура JP2 (12 байт `00 00 00 0C 6A 50 20 20 0D 0A 87 0A`), затем боксы `ftyp` и `jp2h` с `ihdr` (высота, ширина, число компонентов `NC`). Для сырого кодстрима (`FF 4F FF 51`) — маркер SIZ: `Xsiz − XOsiz`, `Ysiz − YOsiz`.
- Альфа: `NC = 4` или бокс `cdef` с типом непрозрачности. Анимации нет.
- Ограничение: кодировщик для JP2 — ffmpeg (декодирование через OpenJPEG). Нужен тестовый набор JP2 (с альфой и без, сырой кодстрим и JP2-контейнер).
- После изменения: обновить `FormatRegistry` (`AnalysisGroup = 'Binary'`), памятку `.docx` и `tests.txt` (4.4.x).
